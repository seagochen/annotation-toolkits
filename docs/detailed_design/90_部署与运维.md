# 部署与运维

## 1. 安装

后端与前端是两个独立进程，各自安装依赖：

```bash
# 后端：只审核/检查/定版和运行除 ReID 抽取外的任务类型，不需要视频抽取/训练依赖
pip install -e 'backend[test]'

# 需要 ReID 的视频抽取、候选挖掘（含参考检测流水线）时
pip install -e 'backend[extract,ultralytics]'

# 前端
cd frontend && npm install
```

无凭证/密钥需要配置——本平台没有认证体系（见
[`10_通用设计.md`](10_通用设计.md) §3）。

## 2. 启动

```bash
export ANNOTATION_WORKSPACE=~/annotation-workspace   # 不存在也可以，第一次创建项目时生成
export ANNOTATION_IMPORT_ROOTS=/mnt/datasets         # 可选：允许关联的服务器目录
uvicorn annotation_platform.server:app --app-dir backend --reload
```

项目在 Web 界面上创建和管理，不需要手写注册表；工作区布局与两个环境变量的约束见
[`80_配置参考.md`](80_配置参考.md) §1、§4。想直接看示例项目时，可以把
`ANNOTATION_WORKSPACE` 指向 `backend/configs/projects.example.yaml`（YAML 文件会被
当作注册表本身）。

```bash
cd frontend && npm run dev
```

两个命令行的完整参数、CORS 跨域配置见 [`80_配置参考.md`](80_配置参考.md) §4 与
根 [`README.md`](../../README.md) 快速开始。前后端分开部署（不同主机/端口）时，
除了 `ANNOTATION_CORS_ORIGINS` 要包含前端来源，深度任务读取基线图的 `<img>` 还
依赖 `crossOrigin`（见 [`10_通用设计.md`](10_通用设计.md) §3），这一点已经在前端
代码里处理，不需要额外部署配置。

## 3. 打包

前端生产构建：

```bash
cd frontend && npm run build
```

产物是静态文件，可用任意静态文件服务器托管；需要在构建时设置
`VITE_API_BASE_URL` 指向实际的后端地址；静态构建完成后改变环境变量不会改写产物。后端没有专门的打包步骤——`pip install`
一个可编辑或非可编辑安装即可，用 ASGI 服务器启动 `annotation_platform.server:app`。
当前按单后端进程运行，不能用增加 worker 的方式安全共享同一数据集；进程内锁、
备份及故障域见[总体部署设计](../overall_design/90_部署与演进.md)。

### 3.1 Docker 镜像（GPU）

仓库根目录的 [`Dockerfile`](../../Dockerfile) 是两阶段构建：

| 阶段 | 基础镜像 | 内容 |
|---|---|---|
| `frontend` | `node:20-bookworm-slim` | `npm ci` 后直接 `tsc --noEmit && vite build`（不走 `npm run build`：其中的 `generate:api` 需要导入 Python 后端；`openapi.json`/`schema.d.ts` 已入库，漂移由 `npm test` 拦截） |
| 运行时 | `nvidia/cuda:12.6.3-cudnn-runtime-ubuntu24.04` | Python 3.12 venv；cu126 版 `torch`/`torchvision`；后端运行依赖 + `extract`/`ultralytics` extras，其中 `onnxruntime` 换成 `onnxruntime-gpu`（两者装在一起会互相覆盖同名包）；前端产物位于 `/app/frontend` |

运行约定：

- `uvicorn` 监听 `0.0.0.0:3000`，`ANNOTATION_FRONTEND_DIST=/app/frontend`，前后端同源，
  不需要配置 CORS。
- `/data` 是工作区（`ANNOTATION_WORKSPACE=/data`），挂载宿主机目录
  （`build_and_run.py --data`，不存在时由脚本创建）；空目录即空项目列表，
  `projects.yaml` 与 `projects/<id>/` 由 Web 界面写入，上传的图片也在其中。
- 已有数据集用 `--mount` 以相同路径挂载进容器，脚本同时把它们和 `/data` 一起写进
  `ANNOTATION_IMPORT_ROOTS`，项目才能在界面上关联这些目录；未挂载的宿主机路径在
  容器里不存在，也就无法关联。
- 容器以非 root 用户运行，UID/GID 由 build arg `APP_UID`/`APP_GID` 指定（默认
  1001）。`build_and_run.py` 用当前用户的 UID/GID 构建，标注结果在宿主机上的属主与
  直接运行时一致。
- `entrypoint.sh` 启动时打印 GPU 可见性，没有 GPU 时照常作为 CPU 服务启动；
  `HEALTHCHECK` 请求 `/api/projects`（注册表无效时为 unhealthy；空工作区是健康的）。

```bash
python3 docker/build_and_run.py --data <dir>              # 构建并（重新）启动
python3 docker/build_and_run.py --data <dir> --no-build   # 只重启容器
python3 docker/build_and_run.py --data <dir> --bind 127.0.0.1 --no-gpu
```

脚本启动后会等待 HTTP 就绪，并在容器内检查 `torch.cuda.is_available()` 与
`onnxruntime.get_available_providers()`。平台没有认证（见
[`10_通用设计.md`](10_通用设计.md) §3），`--bind` 默认 `0.0.0.0`，即同一网络内
任何人都能访问并提交标注。

ReID 的 `train`/`evaluate` 动作调用配置中指定的外部 Python 解释器与训练仓库，容器内
默认不存在这些路径；需要在容器内运行时，把对应目录与解释器环境一并挂载。

## 4. 停启

- 后端：`uvicorn` 进程，标准 `SIGTERM`/`Ctrl+C` 停止；ReID 后台任务用线程执行
  （见 [`30_ReID流水线.md`](30_ReID流水线.md) §4），进程终止时未完成的任务不会
  继续，下次启动加载任务历史时会被标记为 `failed`（"interrupted: platform
  restarted"）。
- 前端：开发服务器同理；生产构建是静态文件，停启由托管方决定。

## 5. 日常运维

- **备份**：所有状态都是本地文件（JSON 侧车、CSV、PNG），标准文件系统备份策略
  即可，无需数据库层面的运维。备份工作区目录即覆盖注册表、全部项目配置和托管数据；
  关联目录模式的项目，其图片与标注结果在被关联的目录里，需要单独备份。
- **日志**：ReID 后台任务的日志写在 `Job.log` 里，随任务历史一起持久化在
  `<dataset>/.jobs/`；`uvicorn` 自身的访问日志走标准输出。
- **清理**：项目配置在 Web 界面的属性页修改（表单或原始 YAML）；删除项目会移除
  `<workspace>/projects/<id>/`，但不会删除关联目录。服务端仍可直接编辑 YAML——
  训练器/评估器路径等 server_only 键只能这样修改（见
  [`70_外部接口.md`](70_外部接口.md)"项目管理"）。没有需要显式"清缓存"的中间状态。
- **监控**：`GET /api/projects/{id}` 的 `status` 字段（`missing`/`empty`/
  `reviewing`/`reviewed`）是最直接的健康信号，见
  [`70_外部接口.md`](70_外部接口.md)。
